# Southbag OS

A desktop operating system for Southbag. The machine is a thin client, the
account is the device, and there is no local user.

Milestone 1 is the boot-to-desktop moment and the shell around it. It runs in a
browser because that is the fastest way to iterate on the shell, not because
the OS is a website.

## Running it

```sh
bun install
bun run dev
```

`bun run build` type-checks, builds, and enforces the bundle budget.

## Bundle budget

Lightweight is the product, not an optimisation pass. `budget.json` sets a
gzipped ceiling per bucket and `bun run build` fails if any bucket is over.
Raising a number is a tracked diff; say why in the commit message.

| Bucket | Ceiling |
| --- | --- |
| JavaScript | 80 KB |
| CSS | 14 KB |
| Fonts | 60 KB |
| HTML | 3 KB |

## Constraints

- **Target runtime is WPE WebKit via `cog`, not Chromium.** Develop against a
  normal browser, but check features against WebKit before adopting them and
  keep polyfills out. No View Transitions API, no `text-wrap: balance`, no
  `backdrop-filter` (supported, but a full-surface per-frame composite is not
  free on 2013 integrated graphics).
- **Deploys to `/os/`.** `base` is set in `vite.config.ts`; asset URLs in
  `index.html` go through `%BASE_URL%`.
- **No backend.** State lives in `localStorage`.
- **Fonts are self-hosted and subset.** The device boots offline.
- Performance is measured on a throttled CPU and a capped memory profile, not
  on the development machine.

## Signing in

The shell does not open without a signed-in Southbag account. Sign-in is
OpenID Connect against Southbag Identity (identity.southbag.cc):
authorization code + PKCE, no client secret — a device cannot keep one, so
the shell is a public client. Each deployment registers itself once through
Identity's dynamic client registration and remembers its client id.

The id token's signature is verified against Identity's published keys before
anyone is called a customer; `state`, `nonce`, issuer, audience and expiry
are all checked. The session lives in `localStorage` until the token expires,
and signing out forgets it — a secretless client cannot revoke, so it forgets.

On the device the shell is served from `http://127.0.0.1:8080`, an origin
Identity does not CORS-trust, so registration, the code exchange and the key
fetch go through `image/shell-extra/cgi-bin/identity-auth`, which forwards
exactly those three calls and nothing else. The authorize redirect itself is
a top-level navigation and needs no help.

`?identity=<origin>` runs the flow against another Identity instance (used to
test against a local one); `?identity=reset` clears the override.

## Storage

There is no local file storage for the customer. Files is Southbag Drive
(drive.southbag.cc), and nothing the customer writes survives a reboot
anywhere else. What that means today, exactly:

**Live boot (the supported configuration).** A read-only squashfs under a
writable overlay that lives in RAM and dies with the power. The shipped
boot line adds `nopersistence`, which refuses live-boot persistence
volumes even if `persistence` is added at the boot prompt - every
persistence path in live-boot 1:20250815 (trixie) is guarded on
`NOPERSISTENCE`. Live boots never touch swap partitions either (live-boot
only activates swap when the `swap` parameter is given, and it is not).
Someone who *edits* the shipped line at the boot menu removes the
refusal; there is no bootloader password, so this is not a boundary
against a person standing at the machine.

**Installed copy (best-effort, not audited end to end).** The installer
copies this filesystem to disk, and the image ships the rules that keep
customer state off that disk: `/home/customer` and `/tmp` are tmpfs
mounts (generated by `image/config/hooks/normal/0015-immutable.hook.chroot`)
and the journal is volatile
(`image/config/includes.chroot/etc/systemd/journald.conf.d/no-local-logs.conf`).
Not covered: the installed system partition itself stays writable -
updates have to go somewhere, and read-only root with dm-verity/A-B
remains the target-platform roadmap; any swap the installer creates is
the installer's own business; removable media would need root and no
automounter, file manager or sudo ships.

**Within a boot.** Scratch space - browser cache and profile, a download
saved mid-session - lives under the customer's home or /tmp, so it is RAM
too and gone at shutdown. Sign-in is per boot by construction: the
shell's session lives in the browser profile under the customer's home,
so every boot starts at the login gate. Keeping anything means putting
it in Southbag Drive.

## Apps

Most apps are the institution's existing web services, opened live at their
own origins rather than re-implemented here. Nothing is framed: a service
always opens as a top-level window. Off the device that is a new browser
window. On the device (image/shell-extra/cgi-bin/launch) the window belongs
to whichever runtime the image ships:

* **Southbag Browser installed**: each service opens as one of its app
  windows (`southbag-browser --app=<url>`) — a real top-level window with
  no tab strip or omnibox, on the full browser stack: the same Southbag
  Identity login as the shell, single sign-on into every southbag.cc
  service, Southbag Secure, browsing fees and Rewards. The Browser app
  launches the whole browser; opening a service that is already open
  focuses its window.
* **Otherwise**: the session starts a cog process per app pointing at the
  shell's Browser web app (src/apps/Browser.svelte) — a window with a
  location bar that becomes the site it visits.

| App | Opens |
| --- | --- |
| Files | drive.southbag.cc |
| Banking | banking.southbag.cc |
| Office | office.southbag.cc |
| Chat | social.southbag.cc |
| Code | code.southbag.cc |
| Branch locator | branch-locator.southbag.cc |
| Lore | lore.southbag.cc |
| Browser | the Southbag Browser web app itself |

Terminal, Kevin and Settings have no web service and stay placeholders until
they are built. The standalone Southbag Browser and Terminal products are
Electron desktop applications (SouthbagHQ/browser, SouthbagHQ/terminal);
images that include the browser get the app-window behaviour above, images
without it keep the cog path — the OS works either way.

## Structure

The shell is four surfaces, composed in `src/Desktop.svelte` and nowhere else.
Under `labwc` each is a separate layer-shell client, so nothing here may depend
on them sharing a page or being able to measure one another.

```
src/
  Desktop.svelte          composition root, and the only file that knows
                          the surfaces currently share a document
  surfaces/
    boot/                 power-on to greeting
    wallpaper/
    panel/
  platform/               identity, clock — everything an app receives
  styles/tokens.css       the institution's design tokens
```

`src/styles/tokens.css` extends the token set in `SouthbagHQ/website`. It does
not define a second design system.

### The boot travel

The mark starts centred and ends as the panel launcher, in one continuous
transform. The flight path is resolved entirely in CSS from shared panel
geometry tokens, so neither surface measures the other — a layer-shell client
cannot read another surface's layout, and the browser build must not rely on
being able to.

Timings live in `src/surfaces/boot/sequence.svelte.ts`. In development,
`?boot=6` stretches both the beats and the travel so the sequence can be
watched.

## Building and installing

The ISO is built by CI on every push that touches the image or the shell, and
uploaded as a workflow artifact. To build it yourself you need Linux with
Docker; it cannot be built on macOS.

```sh
bun run build:device
./image/build.sh
```

The result is `out/southbag-os.iso`. Write it to a USB stick — this destroys
everything on the target device, so check the identifier twice:

```sh
# Linux
sudo dd if=out/southbag-os.iso of=/dev/sdX bs=4M status=progress conv=fsync

# macOS: the r-device is the raw one, and is far faster
diskutil unmountDisk /dev/diskN
sudo dd if=out/southbag-os.iso of=/dev/rdiskN bs=4m status=progress
```

The ISO offers two things. Booting live runs the OS off the stick and touches
nothing. The installer copies that same filesystem onto the disk, so what ends
up installed is this image rather than a stock Debian reassembled from
packages.

**amd64, UEFI only.** It will not boot on an Apple Silicon Mac, and there is
no BIOS/CSM path.

## Target platform

Debian stable, systemd, Wayland, no X11. `labwc` owns compositing, input and
window geometry. The shell is a layer-shell surface; each Southbag app is its
own `cog` window. No display manager — a systemd user session with autologin.
systemd-boot, UEFI only. A/B partitions with dm-verity, read-only root,
`systemd-sysupdate`, images built with `mkosi`.

2013-era Intel graphics are fine on modern Mesa and Wayland. NVIDIA of that
vintage on nouveau is not.
